## Goal
A candidate can fill in and edit their profile and skills. The candidate home page (`/candidate/`)
welcomes them and links to the things they can do.

## Requirement
FP-CAN-1 (profile part). Rule text (brief section "3. Candidate workflow", FP-CAN-1 "Candidate
profile and resume", first paragraph):
> A candidate **MUST** be able to view and edit only their own profile, including a display name and a list of technical skills. Skills **MUST** be saved and available to the matching function.

Skill normalisation is the brief's FP-MATCH-1 rule (owned by T11, `app/skills.py`):
> Normalize candidate and required skills by trimming surrounding whitespace, converting to lowercase, removing empty values, and removing duplicates.

DEFAULT (not in brief): the brief sets no field limits. Keep: headline max 120, location max 80,
summary max 2000, timezone must be a valid IANA name (use `zoneinfo.available_timezones()`), skills:
comma separated, at most 30, each 1 to 40 chars after normalising.

Decided (D16): the editable profile includes the display name. `save_profile` takes a
`display_name` parameter and updates `users.display_name` (1 to 80 chars after strip, DEFAULT (not
in brief)) in the same transaction; the profile form has the field.

## Contract

```python
    # updates users.display_name (1 to 80 chars after strip, DEFAULT (not in brief)) in the same transaction
```
Routes: `candidates.today` GET `/candidate/` (the candidate home), `candidates.profile` GET/POST
`/candidate/profile`. Both `@login_required` and `@role_required("candidate")`.

## Steps
1. Tests first.
2. `get_profile`: read `candidate_profiles` (create nothing; if the row is missing return defaults),
   join skills.
3. `save_profile`: strip all text, validate (collect all errors), `parse_skill_list`, then in one
   transaction: upsert profile (`INSERT ... ON CONFLICT(user_id) DO UPDATE`), delete old
   `candidate_skills`, insert new ones via `get_or_create_skill_ids`, audit `profile.update`.
4. Profile page: form with display name plus the five fields (timezone as a `select_field` of
   `sorted(zoneinfo.available_timezones())`), current skills shown as badges, errors per field.
5. Candidate home (`candidates.today`, template `candidates/today.html`): a heading with the
   display name and simple links to Recommendations, My applications, Profile and Resume. A plain
   landing page, not a dashboard (the activity log and Today widgets are descoped, D22).

## Tests (`tests/unit/test_can_profile.py`)
- save then get returns the same values (including an edited display name); skills normalised, deduped, sorted
- each limit: one character over gives a field error; nothing saved (display name: empty and 81 chars rejected)
- invalid timezone `Mars/Base` rejected
- skills text with 31 skills rejected
- saving again replaces skills (old ones gone)
- employer session GET `/candidate/profile` gives 403; signed out gives redirect to login
- POST profile form via `csrf_post` saves and redirects with a flash
