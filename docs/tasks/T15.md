# T15 · Employer applicants list and status changes

| Phase | Lane | Depends on | Joins lanes | Status |
|---|---|---|---|---|
| 3 | EMP + CAN + MATCH | T11, T14 | yes | READY after T11, T14 |

## Goal
An employer sees the applicants for one of their jobs, with the fields and order the brief requires,
and moves an application through allowed statuses via a confirm screen.

## Requirement
FP-EMP-3: applicant fields, order, status and role. Rule text (brief section "4. Employer
workflow", FP-EMP-3 "Applicant management"):
> For each owned job, an employer **MUST** be able to view its applicants sorted by match score from highest to lowest. Each row **MUST** show candidate identity, skills, match score, application status, and interview booking (if any).
>
> The employer who owns the job **MUST** be able to set an application to one of exactly these statuses: `Pending`, `Interviewing`, `Rejected`, or `Accepted`. Other employers and candidates **MUST NOT** be able to change the status.

Tie-breakers (brief section "5. Matching contract", FP-MATCH-1):
> Sort by descending score. [...] break employer applicant ties by case-insensitive candidate display name and then stable candidate ID.

Decided (per the quotes):
- Order (D15): score high to low, then case-insensitive candidate display name, then candidate ID.
- Fields (D11): `list_applicants` returns dicts with exactly these keys: `application_id`,
  `candidate_id`, `candidate_name`, `headline`, `skills` (the candidate's normalised skill names,
  sorted), `score`, `matched`, `missing`, `status`, `applied_at`, `booking` (the booked slot's
  `{"slot_id", "starts_at", "ends_at"}` as a dict, or `None`). There is no `resume_id` and no resume
  link: the resume is private to the candidate (D10). Of these the brief requires identity
  (`candidate_id`, `candidate_name`), `skills`, `score`, `status` and `booking`; the key names and
  the extras `headline`, `matched`, `missing`, `applied_at` are DEFAULT (not in brief).
- Statuses (D11): exactly `pending`, `interviewing`, `rejected`, `accepted`.
- No transition rules (D11): `set_status` accepts any status in `STATUSES` other than the current
  one (`ValidationError({"status": ...})` otherwise).
- FP-SCHED-2: "If a booked application later leaves `Interviewing`, its booking **MUST** remain
  associated with the application and the slot **MUST** remain unavailable." So changing status
  never touches bookings.
- Another employer (D9): `get_owned_job` raises `Forbidden`.

DEFAULT (not in brief): dates shown in UTC.

## Contract
```python
def list_applicants(conn, employer_id: int, job_id: int) -> list[dict]
def set_status(conn, employer_id: int, application_id: int, new_status: str) -> None
```
Routes: `applications.applicants` GET `/employer/jobs/<int:job_id>/applicants`;
`applications.confirm_status` GET and `applications.set_status` POST
`/employer/applications/<int:application_id>/status` (the target status in a `to` query or form
field), all `@role_required("employer")`.

## Steps
1. Tests first.
2. `list_applicants`: `get_owned_job` first (`Forbidden` if another employer's). One query for the
   applications with candidate name and headline, one query for all those candidates' skills, one
   query for the bookings of those applications (joined to `interview_slots`); score each with
   `engine.score` against the job's skills; sort by the rule; return dicts with exactly the listed
   keys.
3. `set_status`: load the application joined to its job's company; not the owner: `Forbidden`.
   `new_status` not in `STATUSES`, or equal to the current one: `ValidationError({"status": ...})`.
   Update and audit `application.status` with detail `"<old> -> <new>"`. Never touch bookings.
4. Applicants page: table (fields above; dates in UTC), one link per status (other than the current
   one) to the confirm page. Every POST form includes `csrf_field()`.
5. Confirm-status page: `confirm_box` "Change <name>'s application from <old> to <new>?", POST form.
