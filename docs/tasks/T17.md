## Goal
When two eligible candidates try to book the same slot, exactly one succeeds and the other gets the
brief's conflict contract (`409`, `Slot already booked`), and the database never holds a double
booking. (One candidate booking twice is handled earlier as ineligible, D14.)

## Requirement
FP-SCHED-3: booking conflict contract. Rule text, verbatim (brief section "6. Applications and
interview scheduling", FP-SCHED-3 "Atomic concurrency"):
> Booking **MUST** be atomic at the database layer. Use a transaction plus row locking, optimistic concurrency, a uniqueness constraint, or an equivalent database mechanism. An in-process check alone is insufficient.
>
> When two eligible candidates concurrently attempt to book the same slot, exactly one attempt **MUST** succeed, the other **MUST** fail with conflict status (HTTP `409` or a clearly documented equivalent) and the message `Slot already booked`, and the database **MUST** contain exactly one booking afterward. Students **MUST** write unit tests for the booking conflict-handling logic. Database atomicity is verified through implementation review and the running system; students are not required to provide a synchronized multi-client test.

Worked examples: none in the brief beyond the scenario in the second paragraph.

- Status code (D14): HTTP `409`.
- Message or body (D14): the message `Slot already booked` (exact text).
- What the losing user sees next (DEFAULT, not in brief): re-render `scheduling/book.html` with the
  message, status 409.
- Same candidate booking twice (D14): refused as `Forbidden` by the no-existing-booking eligibility
  condition (FP-SCHED-2), not the FP-SCHED-3 conflict.
- Mechanism: "a transaction plus row locking, optimistic concurrency, a uniqueness constraint, or an
  equivalent database mechanism"; Step 2's `BEGIN IMMEDIATE` plus the unique index on `slot_id`
  satisfies this. "An in-process check alone is insufficient."

## Steps
1. Tests first, built from the brief's contract text.
2. In `book_slot`, inside `transaction(conn, immediate=True)`: re-check the slot is free with a
   SELECT; if booked: raise `Conflict(<brief message>)`. Also wrap the INSERT: on
   `sqlite3.IntegrityError` raise the same `Conflict`. Log `booking.conflict` in a **separate** small
   transaction after the rollback (the first one is rolled back).
3. Route: catch `Conflict` and return exactly the brief's status code and message (render
   `scheduling/book.html` with the message, or the format the brief says).

## Tests (in `tests/unit/test_sched_booking.py`; remove the FP-SCHED-3 skip)
- `test_fp_sched_3_conflict_contract`: candidate A books slot S; candidate B (also eligible for the
  same job) books S: gets the brief's status and message; still exactly one booking row; A's booking
  unchanged; a `booking.conflict` audit row exists.
- two connections: open a second `sqlite3` connection to the same file, start `BEGIN IMMEDIATE` on
  it, insert a booking for S, commit; then `book_slot` on the first connection gives `Conflict`.
- the same candidate booking twice is refused as `Forbidden` by the no-existing-booking condition
  (D14), not the conflict path.
