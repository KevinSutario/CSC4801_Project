# T06 · Authorization sweep (FP-AUTH-3)

| Phase | Lane | Depends on | Joins lanes | Status |
|---|---|---|---|---|
| 3 | security | T10, T15, T16 | yes | READY after T10, T15, T16 |

## Goal
Prove, route by route, that nobody can read or change what is not theirs, and that missing objects
give 404. This task only writes tests. Holes it finds are reported, not fixed here.

## Requirement
FP-AUTH-3: authorization and missing object. Rule text (brief section "2. Roles and
authentication", FP-AUTH-3 "Server-side authorization"):
> Every protected operation **MUST** enforce role and ownership on the server; hiding a button in the UI is not sufficient. The observable response contract is:
>
> - unauthenticated request: `401 Unauthorized` or redirect to login;
> - authenticated user with the wrong role or owner: `403 Forbidden`; and
> - missing object that the caller would otherwise be allowed to access: `404 Not Found`.
>
> For non-HTTP frameworks, the UI and service layer **MUST** provide equivalent, clearly distinguishable outcomes.

The brief also names the boundaries this sweep must cover (section "7. Security requirements",
FP-SEC-1 "Object access"):
> Changing an object ID in a request **MUST NOT** bypass FP-AUTH-3. Unit tests of the authorization logic **MUST** cover these representative boundaries:
>
> 1. one candidate cannot read or modify another candidate's resume or application;
> 2. one employer cannot modify another employer's job or read its applicant list;
> 3. a candidate cannot book a slot using another candidate's application.

Expected codes, from the quote: signed out: `401 Unauthorized` or redirect to login; wrong role or
wrong owner: `403 Forbidden`; missing object the caller could otherwise access: `404 Not Found`.

Decided (D9): another user's object gives `403 Forbidden`; a missing object gives `404 Not Found`.
Exceptions the sweep encodes: `candidates.resume_view` gives 403 for any id that is not the caller's
own, including a missing id (Forbidden is checked before existence, D10); `jobs.detail`,
`applications.confirm` and `applications.submit` have no owner, so user B with A's id is 200 (or 302
after a successful submit), not 403.

## Steps
1. From `scripts/contracts.json`, list every endpoint with a path parameter. For each, write down:
   the role that may use it, how to make an object owned by user A, and the URL.
2. `test_authz_sweep.py::test_fp_sec_1_object_access_boundaries`: one parametrised test over that
   list. For each route: user B (same role) with A's id gives 403; right role, missing id (999999)
   gives 404; wrong role gives 403; signed out redirects or 401. Exceptions: `candidates.resume_view`
   gives 403 for any non-own id including a missing one; `jobs.detail`, `applications.confirm` and
   `applications.submit` give 200/200/302 for user B with A's id (no owner). The three brief
   boundaries (candidate vs another's resume/application; employer vs another's job/applicants;
   candidate booking with another's application) each appear as a named case. Use factories and
   `login_as`. POSTs use `csrf_post`.
3. A second parametrised test: every route without a path parameter, wrong role gives 403 and signed
   out redirects or 401.
4. `test_auth.py`: remove the skip on `test_fp_auth_3_authorization_and_missing_object` and make it a
   short, readable version of the sweep for the main cases (employer B edits A's job; candidate B reads
   A's application; candidate opens an employer page; missing job).
5. Run. Every failing case is a real hole: list each in your reply under `BUG:` with the route and
   what happened. Mark those cases `@pytest.mark.xfail(strict=True, reason="B<n>: <route>")` so the
   gate passes and the hole stays visible. The bug cards remove the xfail when fixed.
