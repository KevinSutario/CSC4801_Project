## Why this is a CC card (not a T card)
The CV-file feature needs a new table, so it touches `app/schema.sql` and
`docs/plan/03-DATA-MODEL.md`, which froze after Phase 1 (AGENTS.md rule, DIVISION.md). Only a
contract-change card run by **P2** may touch frozen skeleton/contract files. This card makes the
schema and contract room; the feature logic lands later in T23 (P1) and T24 (P2). It is the first
card in Phase 6 and every other Phase-6 card depends on it.

## Goal
After this card, the database has a one-row-per-candidate `resume_files` table, the data-model and
contract docs describe the new CV-file service and routes, and `scripts/contracts.json` lists the
new names, endpoints and exact test names for T23 and T24 so `check_contracts.py` and the phase
gate can find them. No feature behaviour is built here.

## Requirement
Supports FP-CAN-1 (candidate workflow). The brief's FP-CAN-1 second paragraph already says
"PDF upload and extraction are optional"; the course clarification (2026-11-24) adds a graded
privacy contract for the direct resume URL/API:
> Direct resume URL/API (FP-CAN-1): only the owning candidate may read or edit it. Everyone else
> gets 403. This is graded.
> Employer viewing an applicant's resume: you are encouraged to let the employer of the job the
> candidate applied to view their resume. This is not graded and not a valid peer-audit finding.

This card only encodes the data shape and names; the 403 behaviour is proven in T23/T06, the
employer view in T24.

## Decided (D23, this card records it)
- The CV file is **additive**: the raw-text resume (`resumes` table, T08) stays exactly as is and
  still satisfies FP-CAN-1's "enter a raw-text resume" MUST. The file is optional and separate.
- **One CV file per candidate**, stored **on disk** under `UPLOAD_DIR` (already wired in
  `app/__init__.py` / `app/config.py`); only metadata goes in the DB. PDF only.
- The audit action is the existing **`resume.update`** — do **not** add a new action, so the frozen
  `app/audit.py` ACTIONS set is not touched. Detail string distinguishes the event
  (e.g. `"file added: <orig name>"`, `"file removed"`).
- The direct file-download route is **owner-only** (403 for anyone else, like `resume_view`, D10).
  The employer view is a **separate** route under `/employer/...` (T24), scoped to the employer's
  own job's applicants, and is ungraded.

## Schema to add (`app/schema.sql`, byte-for-byte mirrored into `03-DATA-MODEL.md`)
Add directly after the `resumes` table:
```sql
CREATE TABLE resume_files (
  owner_id      INTEGER PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
  stored_name   TEXT NOT NULL,          -- opaque name on disk under UPLOAD_DIR (never user input)
  original_name TEXT NOT NULL,          -- the candidate's filename, for display/download only
  content_type  TEXT NOT NULL,          -- 'application/pdf'
  size_bytes    INTEGER NOT NULL,
  updated_at    TEXT NOT NULL
);
```
Keep `resumes` unchanged. `PRIMARY KEY (owner_id)` gives the one-file-per-candidate rule and the
`ON DELETE CASCADE` matches `resumes`. Update the ER diagram line in `03-DATA-MODEL.md`:
`users (candidate) 1 ─ 0..1 resumes` gains `1 ─ 0..1 resume_files`.
